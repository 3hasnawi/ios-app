# Shared payroll columns: staged design (not activated)

## Current state

Backup versions 1–6 remain unchanged. `SharedPayrollColumns` in C# and Swift is a tested byte-preserving primitive, not a database migration, backup reader, or writer. Production must not emit a new backup version until both client implementations, server capability checks, and device recovery tests are complete.

`SharedPayrollCandidate` creates and validates a separate v7 candidate from an existing ZIP and can reconstruct a new legacy ZIP. `CreateMerged` accepts explicitly provided replacement-entry streams, verifies them and preserves all other entries; tests use fictional employee and deduction additions and a simulated interruption. It does **not** automatically collect Windows local imports or pending edits, validate all business semantics of caller-supplied replacements, or connect to the application's backup or restore UI. Swift's standalone candidate reader restores packed JSONL records but is not connected to ZIPFoundation or SwiftData. Cross-language tests exchange fictional candidate records in both directions. A 3,000-row artificial fixture shrank from 68,220,740 to 3,109,100 uncompressed bytes including its schema. An optional Linux stress test (`SALARY_RUN_LARGE_CANDIDATE=1`) validated 102,000 artificial records, 2,320,135,740 to 105,265,100 uncompressed bytes, with a 151,171,072-byte process peak working set. These synthetic numbers are not predictions for user data or iPhone behavior. Testing these components does not establish iPhone restore or real-server safety.

`SharedPayrollOverlay` is an unconnected prototype that takes an explicitly supplied `PayrollImportState` and active snapshot and incorporates payroll/deduction months into a separate candidate while copying unaffected source records verbatim. An explicit overload accepts accounts, settings, reconciliation, trust and archive changes; fictional tests cover added, replaced and explicitly removed PDFs, stable IDs, and missing files. It checks the source fingerprint and tests month replacement, but does not itself collect or lock the current stores, or prove application-level safety. It is not a complete backup and must not be exposed or uploaded.

`SharedPayrollSnapshotCapture` is a further unconnected prototype that loads the archive, payroll, link, reconciliation and trust stores; fingerprints local book files and verifies all revisions before and after candidate generation. Its token also permits another check after a future upload. Fictional tests cover collecting all these layers and detecting later changes to an account, a book file and payroll. Checks do not lock stores across the final move/upload, and the caller must recheck before acknowledging a backup; user-device performance, full restore and server behavior are still unverified.

The separate iOS expense-approval ledger uses backup version 8 only when that ledger is present. It retains the existing legacy JSONL payroll representation; it is not the experimental shared-columns version 7. The new iOS reader explicitly rejects version 7 and retains support for versions 1–6, while older iOS releases reject version 8 rather than silently dropping approvals. Device restore and iCloud behavior still require testing.

`BackupReader.ReadCandidate` is an explicit experimental Windows reader. It verifies the original and candidate manifests agree, checks schema and row hashes, and leaves the normal reader rejecting version 7. It still materializes all employee models in memory and is not wired to restore. Crucially, the overlay/capture prototypes require a `BackupSnapshot` obtained through the existing reader, which rejects the reported 2.27 GB entry: therefore they cannot yet migrate that actual backup. A bounded streaming path from the legacy archive and local edits, plus safe staged restoration on both platforms, is required before this can solve the user's case.

The owner has stopped Windows work and selected iPhone with manually saved iCloud Drive backups; do not upload to the server. The standalone Swift candidate writer streams source rows into new files, rejects existing output paths and removes its own incomplete files on error. It is not an app backup, does not update existing data, and is not connected to iCloud or restore. It does not by itself fix the large existing database, SwiftData memory usage or the iOS restore transaction.

## Proposed version 7 representation

* The experimental `SharedPayrollBackupRow` stores an exact Base64-encoded segment corresponding to repeated header bytes once, indexed by uppercase SHA-256. It aligns boundaries to complete Base64 groups and preserves the exact JSON escapes around the segment. A supported row keeps exact bytes before and after that segment. Restoring concatenates those three byte sequences in order and checks the complete row hash; the original bytes, not merely the interpreted values, must be identical. `SharedPayrollColumns` independently splits the underlying header array for identifying the segment.
* Property order, duplicate column names, empty cells, unknown properties, encoding escapes, whitespace, and per-sheet or per-month schema differences are significant. A record that cannot be split losslessly must retain its original `rawColumns` bytes in full. Never infer schema identity from a month, a display label, or a count.
* SHA-256 is over the exact schema bytes, not a normalized title or a locale-specific string. On import, recompute it and reject a missing, duplicate-conflicting, corrupt, or unknown schema reference before any changes are committed. A schema hash does not protect a row's other bytes; the complete backup, each source and output record, and archive entries must have independent integrity checks.
* Layout and file names are intentionally not frozen here. Define limits, final record keys and test vectors jointly with both clients before implementation. Version 7 must be explicitly rejected by existing readers; do not repurpose version 6 or a `rawColumns` payload that old clients could silently misread.

## Migration and activation gates

1. Preserve an independently verified full backup outside the current single-version server. Never mutate its original. The local source and its pending imports must be snapshotted under their existing concurrency guards.
2. Generate the new candidate in a separate file with streaming IO and checksums. Validate all rows and unknown fields, month totals, employee/deduction counts, source file identities, archive PDFs, reconciliation, trust, account and settings state. Decode and compare every original `rawColumns` byte sequence; compare all other fields and file hashes. Abort safely on any mismatch.
3. Before enabling writing, deploy and test readers on iOS and Windows, including a staged, transactional restore that does not require the whole file or all models in memory. The current iOS restore still retains SwiftData changes in one transaction and is not proven suitable for the reported workload.
4. For the owner's current iCloud-only workflow, verify Files access, provider behavior, upload completion and preservation of a separate older checkpoint. Do not contact or upload to the server. Any future server use would separately require explicit capability checks, older-client protection, independent checkpoints and race tests.
5. Exercise old-to-new, new-to-new, and rejection by old clients, along with interrupted disk writes, full disks, corrupted schemas/tails, duplicate names, Unicode, unknown fields, file tampering between validation and commit, and an iPhone physical-device restore of a workload representative of the actual data. Check RAM, disk, runtime and correctness. User data must remain local and never be uploaded for testing.
6. Only after successful validation, expose a clearly reversible migration and retain prior versions per the user's retention policy. If any gate fails, keep the previous state and do not claim a completed backup.
